CARL Overview: Mar 26, 2026

CARL interacts with humans to turn ambiguous instruction sets into executable workflows.

CARL, or Chat Assisted Rubric Learning, is designed for situations where the business objective is clear but the full technical specification is not. It helps domain experts define the right problem, translate it into a formal workflow, and then execute autonomously once the scope is ringfenced.

The current demonstrable version of CARL is designed to solve optimization problems using reinforcement learning (RL).

Why CARL exists

Most applied AI projects fail early for practical reasons: the problem is underspecified, the domain expert does not want to hand-design every detail of the system, the AI makes assumptions to fill the gaps, and hidden issues only surface once implementation is complete. CARL is built to avoid this outcome.

  • It lets the user stay focused on the problem rather than the implementation mechanics.
  • It makes modeling choices explicit and explainable before expensive implementation and/or training starts.
  • It uses theory and benchmarks when available, so performance is measured against something meaningful.

Case study: How CARL works in the reinforcement learning (RL) framework

1. Scopes the problem

CARL asks targeted follow-up questions until the objective, dynamics, constraints, and success criteria are unambiguous.

2. Designs the RL framing

It proposes state variables, action spaces, reward functions, sampling strategies, and architectures that fit the business problem.

3. Delivers working systems

Once aligned, CARL builds the environment, training pipeline, diagnostics, tests, and evaluation artifacts end to end.

How CARL evolved

We started with a basic question: Can today's AI agents reliably implement an RL solution from scratch, if the problem is described to them? We tried the following ideas:

  1. Describe the problem to an agent such as Claude or Codex, and ask it to implement a reusable RL repository
  2. Define a set of skills, explaining how to set up the repository, with common pitfalls and tips, and then ask the same agents to generate the repository
    • That approach proved that end-to-end code generation was feasible, but it also exposed a recurring weakness: important modeling details were often still ambiguous when implementation began
  3. So finally we built CARL, an interactive agent that asks for clarifications, proposes the implementation structure, and works with a finance expert (with no assumptions about AI knowledge) to build a stable solution

What the first two approaches taught us

  • One-shot generation works best when the objective, constraints, state variables, and evaluation logic are already very well specified.
  • In practice, hidden assumptions around rewards, action definitions, benchmarks, and edge cases usually surface only after code starts getting written.
  • That means the first repository draft is often informative, but not yet the right repository.

What CARL changes

  • CARL treats repository generation as the end of the workflow, not the beginning.
  • It uses multiple rounds of human interaction to refine the problem before committing to an RL design.
  • The result is a higher-quality repository because the agent has already pressure-tested the formulation with the user before implementation begins.

How the skill files changed

Zero-shot repository generation

The initial skill files are organized as modular implementation helpers such as repository setup, environment design, agent implementation, training, testing, visualization, and a single end-to-end workflow file.

What this implies: the system is primarily geared toward writing the RL repository quickly and the problem statement is already assumed to be sufficiently specified.

  • The workflow starts from an implementation mindset: define the RL problem, build the environment, train, test, and visualize.
  • Most of the guidance is about code structure, algorithm choice, debugging, and progressive training stages after the formulation is already fixed.
  • This is a strong fit for zero-shot generation, but it leaves less room for clarifying business ambiguities before the repo is created.

CARL: 8-step interactive formulation

The skills for interactive RL are explicitly sequenced as 01_problem_definition through 08_launch, which turns the skill set into a staged operating procedure rather than a flat toolbox.

What this implies: CARL separates understanding the problem from defining the RL system, and only launches full repository generation after several rounds of structured interaction.

  • Steps 1-2 focus on understanding the domain, consulting references, and asking for missing information from the user.
  • Steps 3-7 progressively lock in states, actions, rewards, initial testing, and parameter exploration before full launch.
  • Step 8 is still full repository generation, but it now happens after the formulation has been pressure-tested through the first seven steps.

Takeaway

The shift in the skill files mirrors the larger evolution from zero shot to CARL: the first iteration optimized for generating a complete RL codebase in one pass, while the revised CARL skills optimize for getting the problem definition right before code generation begins. In other words, the older skills are implementation modules, whereas the CARL skills are an interactive decision process that culminates in implementation.

Comparison to existing approaches

Existing RL frameworks already solve important parts of the pipeline, but most of them start after the problem has already been formalized. CARL is differentiated by operating one step earlier: it helps define the problem before committing to the repository.

Stable-Baselines3

Stable-Baselines3 is positioned as a set of reliable PyTorch implementations of RL algorithms, with the RL Baselines3 Zoo adding pre-trained agents and scripts for training, evaluation, tuning, plotting, and recording.

Best fit: fast experimentation once the environment and objective are already specified.

Compared with CARL: SB3 is an algorithm and training toolkit, while CARL is a problem-formulation and repository-generation workflow.

RLlib

RLlib is presented as a production-level, scalable, fault-tolerant RL library with support for multi-agent training, offline data, and externally connected simulators.

Best fit: large-scale or production-oriented RL workloads after the modeling choices have already been made.

Compared with CARL: RLlib focuses on scaling and execution infrastructure, whereas CARL focuses on clarifying the business problem and translating it into the right RL setup.

FinRL

FinRL is described by AI4Finance as an open-source framework for financial reinforcement learning, organized around market environments, agents, and applications with a train-test-trade pipeline.

Best fit: financial trading and portfolio workflows where the task can be mapped into an existing financial RL pattern.

Compared with CARL: FinRL is domain-specific and finance-ready, but CARL is more focused on interactively discovering how an ambiguous finance problem should be framed before implementation starts.

Interpretation

These approaches are not direct substitutes for CARL so much as complements to it. Stable-Baselines3, RLlib, and FinRL are strongest once the state, action, reward, environment, and evaluation design are already known. CARL's claim is that, in real business settings, those choices usually need to be surfaced through interaction first.

Two problems solved

Solved Problem 1

Merton consumption and portfolio optimization

March 7, 2026

This problem asked for the optimal joint choice of risky allocation and consumption over time under CRRA preferences and a terminal bequest motive.

Business relevance: It is a clean test of whether CARL can reproduce a theoretically optimal dynamic asset allocation policy while handling realistic modeling details and implementation failures.

What CARL solved: It translated the economics into an RL environment, used the analytical Merton solution as ground truth, corrected specification and reward-scaling issues discovered during execution, and delivered a model that matched the analytical optimum with near-perfect policy correlation.

Solved Problem 2

Goal-based portfolio selection

March 9, 2026

This problem asked for annual selection from an efficient frontier to maximize the probability of reaching a target wealth goal over a finite horizon.

Business relevance: It is closer to a real application setting because the agent must generalize across different funded ratios, horizons, and portfolio opportunity sets.

What CARL solved: It created a fixed-size state representation for variable frontier sizes, designed a bounded continuous action that snaps cleanly to discrete portfolios, and trained a policy that slightly exceeded the greedy analytical benchmark on goal-achievement rate.
